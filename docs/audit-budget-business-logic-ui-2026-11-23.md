# Budget — аудит бизнес-логики и UI, раздел «Бюджет»

Дата: 2026-11-23. Основа: актуальные исходники `main` перед PR и тесты новой ветки. Это **этап раздела**, а не заявление о завершённом сквозном аудите всех экранов с двумя реальными аккаунтами.

## Что должно быть простым в личном приложении

Два участника, общие операции, импорт выписок, расходы по датам/категориям, обязательные платежи, понятная история и редактирование. Цифры должны быть достоверными, а все необязательные «умные» функции — вторичными, без создания обязательных шагов. Календарь планов не смешивать с расходами.

## Подтверждённые находки: сначала бизнес-логика

| Приоритет | Проблема и доказательство | Что делаем |

| Высокий / исправлено в PR этапа | В `TerraBudget.tsx` при пустом списке платежей подставлялись ипотека 35 000 ₽ и интернет 800 ₽; при пустой аналитике показывались три категории с вымышленными суммами, даже при нулевых реальных тратах. Это не демо-режим, а рабочий рендер. | Убраны фиктивные данные. Пустые состояния честно говорят, что информации нет. |
| Высокий / исправлено в PR этапа | Кнопка «Оплатить» вызывала `onToggleMandatoryPaid`: отметка факта оплаты, не платёж/списание. | Переименована в «Отметить оплаченным». Отдельная доступная кнопка для редактирования. |
| Средний / исправлено в PR этапа | Предыдущий/следующий месяц строился через `Date.setMonth()` без ограничения числа, из-за чего 31 января может перейти в март. | Использован существующий `shiftCalendarMonth`, сохраняющий корректный календарный месяц. |
| Высокий / требует исследования | В `TerraBudget.tsx` месячный `monthBalance` — разница только доходов и расходов этого месяца. Отдельно `ledgerBalance` учитывает остаток из предыдущих месяцев. Нужно явно объяснить «денежный остаток» и «результат месяца» и не подменять один другим. | Пройти реальные сценарии начального остатка, личного и семейного режима, смены месяца; переименовать показатель только после проверки семантики. |
| Высокий / требует исследования | `mandatoryReserve` вычитается из доступного баланса, но в личном режиме `monthlyPaymentStates` фильтрует счета по участнику и может учитывать общие счета; распределение общих обязательств между двумя людьми отдельно не определено. | Проверить с двумя реальными аккаунтами; договориться, что является общим и личным резервом; зафиксировать тесты инвариантов. |
| Средний / требует исследования | `sanitizeTransaction` в `DataContext` превращает некорректные `amount/type/date` в нулевую расходную операцию с текущей датой. Неясно, вызывается ли при импортируемых строках или только при чтении legacy-записей. | Проследить весь путь данных и не заменять реальные невалидные записи молча; сначала тесты импорта и совместимости сохранённых данных. |
| Средний / требует исследования | В `TerraBudget` `categoryBreakdown` использует обычное сложение JS float и только непосредственных дочерних категорий; другие финансовые функции считают копейки целыми. | Сравнить сумму разбиения с месячным расходом на категориях нескольких уровней, копейках и неизвестных категориях; выбрать общий расчёт. |
| Средний / требует исследования | Безопасный дневной лимит, «в темпе», «без перерасхода» и «сэкономлено» при нулевом/неопределённом лимите могут звучать как проверенный финансовый совет. | Разделить вычисляемый ориентир и фактические траты, добавить состояния «не настроено» и «недостаточно данных». |

## UI/UX — сразу после оценки смысла каждого блока

1. **Убрать:** фиктивные показатели, бессодержательные декоративные иконки, градиенты `bg-gradient-to-br` на KPI, сильные `shadow-xl`, лишние `active:scale-95`, повторяющиеся карточки «дневной лимит», «темп», «индикатор», «прогресс», если они сообщают одно и то же.
2. **Оставить наверху:** выбранный месяц, переключатель «Все / участник», приход/расход/результат периода, добавление операции, история. Лимит/резервы — отдельный необязательный информативный блок с понятным источником расчёта.
3. **Переработать:** календарь расходов — не использовать микрошрифт `text-[9px]` и скрытые статусы как основной способ чтения; на узком телефоне показывать меньше информации на день, детали по нажатию.
4. **Единый стиль Terra:** токены `SURFACE_CARD`, `FILTER_RAIL`, `FILTER_CHIP`, одинаковые состояния/отступы/радиусы, минимальные тени, стабильная ширина кнопок, реальные пустые состояния.
5. **Доступность:** карточка редактирования платежа — настоящий `button`, не кликабельный `div`; 44px для действий, явные текстовые подписи, клавиатурный фокус; при необходимости `prefers-reduced-motion`.
6. **Никаких анимаций ради оформления:** Motion допускается только для взаимодействий с проверенной пользой; не трогать скролл и финансовые вычисления.

## Минимальный критерий готовности раздела

- Суммы в рублях и копейках совпадают с исходными операциями; корректный личный/общий режим.
- Добавить, изменить, удалить, импортировать, повторно импортировать и убрать дубли без искажения общего бюджета.
- Отметка обязательного платежа **не создаёт банковскую операцию**; отсутствие платежей/категорий ничего не придумывает.
- Смена месяца 31-го числа работает; долгие списки и имена не ломают ПК/Android/Safari; тестируются пустые состояния и ошибки.
- Исходники → TDD → TypeScript → сборка → браузер → 3 зелёных GitHub CI на точном PR SHA → Git merge → Vercel production READY → продакшен-проверка.

## Порядок следующих разделов

После завершения «Бюджета»: **Обзор → Покупки → Планы и календарь → Чат → Сервисы/настройки/интеграции**. У каждого: бизнес-логика, проверка реально нужного функционала для двух пользователей, что удалить/объединить, UI и подтверждённые тесты. Не добавлять новую функциональность до устранения найденных проблем.

## Ограничения доказательств

Анализ здесь основан на реальном коде и регрессионных тестах. Отдельная браузерная проверка демо не подтверждает Firestore-присоединение второго пользователя, конфликтующие обновления, восстановление старых записей, настоящий банковский импорт и Safari/iOS. Эти пункты до фактического запуска остаются «не проверено».
