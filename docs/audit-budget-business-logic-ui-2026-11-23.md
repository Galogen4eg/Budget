# Budget — аудит бизнес-логики и UI, раздел «Бюджет»

Дата: 2026-11-23. Основа: актуальные исходники `main` перед PR и тесты новой ветки. Это **этап раздела**, а не заявление о завершённом сквозном аудите всех экранов с двумя реальными аккаунтами.

## Что должно быть простым в личном приложении

Два участника, общие операции, импорт выписок, расходы по датам/категориям, обязательные платежи, понятная история и редактирование. Цифры должны быть достоверными, а все необязательные «умные» функции — вторичными, без создания обязательных шагов. Календарь планов не смешивать с расходами.

## UI/UX — сразу после оценки смысла каждого блока

1. **Убрать:** фиктивные показатели, бессодержательные декоративные иконки, градиенты `bg-gradient-to-br` на KPI, сильные `shadow-xl`, лишние `active:scale-95`, повторяющиеся карточки «дневной лимит», «темп», «индикатор», «прогресс», если они сообщают одно и то же.
2. **Оставить наверху:** выбранный месяц, переключатель «Все / участник», приход/расход/результат периода, добавление операции, история. Лимит/резервы — отдельный необязательный информативный блок с понятным источником расчёта.
3. **Переработать:** календарь расходов — не использовать микрошрифт `text-[9px]` и скрытые статусы как основной способ чтения; на узком телефоне показывать меньше информации на день, детали по нажатию.
4. **Единый стиль Terra:** токены `SURFACE_CARD`, `FILTER_RAIL`, `FILTER_CHIP`, одинаковые состояния/отступы/радиусы, минимальные тени, стабильная ширина кнопок, реальные пустые состояния.
5. **Доступность:** карточка редактирования платежа — настоящий `button`, не кликабельный `div`; 44px для действий, явные текстовые подписи, клавиатурный фокус; при необходимости `prefers-reduced-motion`.
6. **Никаких анимаций ради оформления:** Motion допускается только для взаимодействий с проверенной пользой; не трогать скролл и финансовые вычисления.

## Минимальный критерий готовности раздела

- Суммы в рублях и копейках совпадают с исходными операциями; корректный личный/общий режим.
- Добавить, изменить, удалить, импортировать, повторно импортировать и убрать дубли без искажения общего бюджета.
- Отметка обязательного платежа **не создаёт банковскую операцию**; отсутствие платежей/категорий ничего не придумывает.
- Смена месяца 31-го числа работает; долгие списки и имена не ломают ПК/Android/Safari; тестируются пустые состояния и ошибки.
- Исходники → TDD → TypeScript → сборка → браузер → 3 зелёных GitHub CI на точном PR SHA → Git merge → Vercel production READY → продакшен-проверка.

## Порядок следующих разделов

После завершения «Бюджета»: **Обзор → Покупки → Планы и календарь → Чат → Сервисы/настройки/интеграции**. У каждого: бизнес-логика, проверка реально нужного функционала для двух пользователей, что удалить/объединить, UI и подтверждённые тесты. Не добавлять новую функциональность до устранения найденных проблем.

## Ограничения доказательств

Анализ здесь основан на реальном коде и регрессионных тестах. Отдельная браузерная проверка демо не подтверждает Firestore-присоединение второго пользователя, конфликтующие обновления, восстановление старых записей, настоящий банковский импорт и Safari/iOS. ## Этап 2: подтверждённые исправления категорий и семантики результата

- Аналитика `TerraBudget` прежде обходила только категорию и её **непосредственных** детей и складывала суммы через `number`. Вложенность в три уровня скрывала часть расходов, а незнакомые/удалённые категории исчезали из диаграммы. Новый чистый расчёт `buildBudgetCategoryBreakdown` агрегирует дерево по корню, суммирует **в копейках**, сохраняет расходы без категории в группе «Без категории». Невалидные и нерасходные записи в аналитике не участвуют.
- В панели результата месяца заменены вводящие в заблуждение «Свободно», «В норме», «Осталось» на **«Результат месяца»** и «Доходы − расходы». Это не фактический остаток денежных средств, который учитывает начальный баланс и прошлые периоды.
- Если месячных доходов нет, доля расходов в доходах не равна нулю: вместо выдуманных `0%` выводится тире. Краткий заголовок «Расходы к доходам» заменяет «Исполнение бюджета», потому что эти значения не являются план/фактом бюджетных лимитов.
- Для строки «Без категории» нет выдуманного перехода к несуществующему ID категории. Остальные категории сохраняют переход в аналитику.
- Новые тесты проверяют трёхуровневую вложенность, копейки, отсутствующие категории, нерасходные данные, детерминированную сортировку, подписи и непротиворечивый drill-down.

**Не меняли:** существующие Firestore-транзакции, их ID, семейные лимиты, резервы, накопления, импорт и календарь планов.

### Следующий критический шаг перед завершением раздела

Текущий `TerraBudget` рассчитывает `monthlyPaymentStates`, `monthlySalary` и `ledgerBalance` по **отфильтрованным операциям участника**, одновременно вычитая общий `manualReservedAmount` и отображая семейный `BudgetPlanningPanel`. Это подтверждённая неоднозначность областей расчёта и потенциально неверные персональные рекомендации. До изменения семантики требуется тест семейного дневного лимита при переключении «Все / участник», с начальными остатками, уже оплаченными общими обязательствами и накоплениями. Тестового доступа к двум реальным пользователям пока нет.


## Этап 3: семейный остаток не зависит от фильтра участника

**Подтверждённая исходная ошибка:** при выборе участника `TerraBudget` раньше вычислял `ledger` только из его операций, однако вычитал общие семейные накопления и часть обязательных платежей. Общая доступная сумма и «дневной безопасный лимит» менялись от фильтра истории; начальный семейный остаток для конкретного участника был не распределён.

**Исправлено:** чистый расчёт `calculateFamilyBudgetProjection` использует все операции семьи, оплаченные общие обязательства, общий начальный остаток, семейные зарплаты и сбережения в копейках. Вкладка «Все / участник» теперь влияет на видимые операции и их результат за месяц, но не на общий семейный доступный остаток и дневной ориентир. Индикаторы сегодняшних/вчерашних расходов относятся ко всей семье; в UI это прямо написано. Убраны безусловные оценки «В темпе» и сравнение личного результата дня с дневным лимитом всей семьи.

**Автоматическая проверка:** unit-инварианты семейного остатка, частичной/полной оплаты, накоплений; браузерные клики по фильтрам на мобильном 390px и Full HD 1920px в демо-режиме. Full HD smoke закреплён в GitHub CI.

**Ограничения:** тест с двумя *реальными* Firebase-учётными записями и история ранее импортированных выписок не выполнен. В личном приложении пока нет механизма явного распределения общего стартового остатка и резервов между участниками — до появления такого механизма показывать «личный доступный остаток» как точную сумму нельзя. Никакие данные Firestore не мигрировали.
